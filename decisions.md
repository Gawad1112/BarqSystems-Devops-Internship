## Decision
- Choice: Changed the published container port in docker-compose.yml from 81 to 80, rather than changing nginx.conf to `listen 81`.
- Why: Both edits would have resolved the mismatch equally well. I chose the one that ends in a conventional configuration. Port 80 is the standard HTTP port and the default the nginx image expects; 81 was arbitrary and would have surprised anyone reading the config later. Fixing the side that was unusual leaves the system in a more predictable state than fixing the side that was already correct.
- Alternative: Change `listen 80;` to `listen 81;` in nginx/nginx.conf. Functionally identical.
- Trade-off: None technically. The cost of my choice is that anyone comparing my repo to the original baseline sees a change in Compose rather than in nginx.conf, so I have documented which file I changed and why.
- Evidence / commit: 66ea426. Verified before the change with `docker compose -p barq-assessment exec nginx netstat -tulpn`, which showed nginx listening only on `0.0.0.0:80` and nothing on 81.
- Production improvement: The two files agreeing on a port is something that should be enforced rather than remembered. In production I would have the validation script assert that the published container port matches the port nginx is listening on, so a future edit to one file without the other fails CI instead of failing silently at runtime.

## Decision
- Choice: Kept the supplied base images rather than changing them — `python:3.12-slim-bookworm` for the application, `postgres:16-alpine`, `redis:7.4-alpine` and `nginx:1.28-alpine` for the supporting services. All four are pinned by SHA256 digest, and I kept that pinning.
- Why: The slim Debian image for Python carries a much smaller package set than the full image while still using glibc, which avoids the compatibility problems Alpine's musl libc can cause with pre-built Python wheels — `psycopg[binary]` is exactly the kind of dependency that is affected. For the supporting services, Alpine is a sensible choice because they are single-purpose and do not compile anything at runtime. Pinning by digest matters more than the tag itself: a tag like `16-alpine` can be repointed to a new image at any time, so two builds a month apart could differ. A digest cannot change, so my build today and the grader's build next week are byte-for-byte identical. I verified this in practice when checking the Postgres data directory: the image I pulled separately reported the same digest as the one pinned in Compose, which is how I knew the result applied to this project.
- Alternative: Move the application to `python:3.12-alpine` for a smaller image, or to the full `python:3.12` for maximum compatibility. Alternatively, loosen the digest pins to plain tags so images update automatically.
- Trade-off: Digest pinning means security updates are not picked up automatically. An image with a known vulnerability stays in use until someone deliberately updates the digest. That is a real cost, and the answer is not to unpin but to have something watching for it — see the production improvement below.
- Evidence / commit: Digest verified against the running image with `docker run --rm postgres:16-alpine printenv PGDATA`, which reported `sha256:cf78e766...`, matching the digest in docker-compose.yml.
- Production improvement: Pair digest pinning with automated dependency scanning, so pinned images are flagged when a CVE affects them and the digest is updated deliberately rather than drifting silently. I would also add an image scan to CI as the optional extra credit in Part 3 suggests.

## Decision
- Choice: Fixed the health check to call `/health` rather than `/healthz`, and kept the check running inside the container using a Python one-liner over loopback rather than adding curl or wget to the image.
- Why: `/health` is the endpoint the application actually implements, as defined in assessment/APPLICATION.md. The original check requested `/healthz`, which the app correctly answered with 404, and Docker read the non-200 response as unhealthy. The app was never unwell — the check was asking the wrong question. On the tool choice: the check uses `python -c "import urllib.request; ..."`, and Python is necessarily present because it is what runs the application. Installing curl purely for health checks would add a package, and therefore additional attack surface and patching burden, for something the image can already do. This also matches the brief's requirement to use health-check tools installed in the image.
- Alternative: Add curl to the Dockerfile and use `curl -f http://127.0.0.1:8080/health`. More readable, at the cost of an extra dependency.
- Trade-off: The Python one-liner is harder to read than a curl command, and a reviewer has to parse it to see what it does. I consider that acceptable in exchange for not adding a package. There is a second trade-off in what the check measures: `/health` deliberately does not test PostgreSQL or Redis, so a container can be "healthy" while unable to serve real traffic. That is the correct behaviour — liveness and readiness answer different questions — but it means container health alone is not a sufficient signal.
- Evidence / commit: Before the fix, `docker compose ps` showed both apps as `Up (unhealthy)` and app logs showed `"path": "/healthz", "status": 404` repeating every five seconds. After the fix both showed `(healthy)`. Documented in troubleshooting.md Entry 4.
- Production improvement: Docker's health status is only visible to someone running `docker compose ps`. In production the readiness endpoint should be polled by whatever is routing traffic, so an unready instance is removed from rotation automatically, and health transitions should raise an alert rather than waiting to be noticed. I would also reconsider the intervals: 5s with 3 retries means roughly 15 seconds before a failing container is marked unhealthy, which is reasonable here but should be a deliberate choice tied to how quickly traffic needs to drain.

## Decision
- Choice: Enabled upstream retry with `proxy_next_upstream error timeout`, bounded by `proxy_next_upstream_tries 2` and `proxy_next_upstream_timeout 7s`, and enabled passive failure counting with `max_fails=3 fail_timeout=10s` on both servers. Deliberately excluded `http_503` from the retry conditions.
- Why: The historical logs quantify what the original settings cost. During the 11:05–11:09 incident, 40 client requests returned 502 while a healthy backend was serving throughout, and in the same window 19 requests on `/ready` and `/instance` were retried and all 19 succeeded. Retry was not a theoretical improvement — it was already working on two endpoints and absent on the four that users actually depend on.

  The exclusion of `http_503` comes from the same evidence and is the more considered half of the decision. The 47 requests that returned 503 in that dataset failed because Redis timed out or PostgreSQL rejected credentials. Both application instances share one Redis and one PostgreSQL, so retrying a 503 on the other instance reaches the same broken dependency, fails identically, and doubles the load on something already struggling. Retry is the right response to an instance-local fault and the wrong response to a shared one, and the condition list is where that distinction gets encoded.

  `timeout` was the genuinely arguable inclusion. Against it: incident 4 showed both backends timing out on `/records` simultaneously, where a retry would have roughly doubled the client's wait for the same eventual 504. For it: one instance hanging while the other is healthy is the more common failure and is exactly what retry exists for. I included it, on the basis that the downside is bounded by the tries and timeout limits while the upside is unbounded. It was justified faster than expected — the first live failover test produced an attempt that timed out at `proxy_connect_timeout` and returned `504, 200`, which `error` alone would not have retried.
- Alternative: `proxy_next_upstream error` only, which is the conservative choice and avoids compounding slow failures. Or including `http_503`, which would mask dependency failures behind retries and make them harder to detect. Or leaving `max_fails=0` and relying solely on retry, which rescues individual requests but keeps feeding traffic to a dead backend indefinitely.
- Trade-off: Retry makes a failing system look healthier than it is. A backend that fails every request still returns 200 to clients as long as the other survives, so the fault becomes invisible at the edge — which is why `max_fails` matters alongside it, and why the production improvement below is about alerting rather than more retry. There is also a correctness consideration: `proxy_next_upstream` will retry non-idempotent requests, so a `POST /records` retried after a timeout could create a record twice. `non_idempotent` is not in my condition list, so NGINX only retries a POST when it is certain the request was never sent, which is the safe default.
- Evidence / commit: 27db67f. Verified with `nginx -T` that all six settings are present in the running configuration. Live test with app-02 stopped: 30/30 requests served by app-01, 30/30 HTTP 200, zero client-visible 502s, versus the 40 client 502s the historical logs record under the original settings. Nginx logs showed both retry signatures — `"502, 200"` at 1.069 s and `"504, 200"` at 2.005 s. Documented in troubleshooting.md Entry 11.
- Production improvement: Passive health checking is the structural weakness here. NGINX open source cannot poll a backend's `/health` endpoint; it only learns a server is bad by sending it a real client request that fails, so the first failure after an instance dies is always paid for by a real user. `proxy_next_upstream` conceals that from the client but does not prevent it. In production I would use active health checks — available in NGINX Plus, or by moving to HAProxy or a service mesh — so an unhealthy instance is removed from rotation before any client request reaches it. I would also alert on the retry rate itself: a rising count of comma-separated upstream entries in the access log is an early signal of an instance degrading, and it is currently only visible to someone reading the logs.

## Decision
- Choice: Raised `proxy_read_timeout` from 3s to 4s, and sized `proxy_next_upstream_timeout` at 7s rather than at the 8s ceiling the other settings already imply.
- Why: The historical logs give a measured figure to tune against rather than a guess. In the 11:25–11:26 incident, NGINX returned 504 to eight clients after 2.001 s while the applications completed those same requests successfully at 2700 ms — the client received a failure for work the application had finished. A read timeout below the endpoint's real worst-case response time manufactures failures out of successes. At 3s my margin over that measured 2700 ms was 300 ms, which is thin for an endpoint I have direct evidence can take 2.7 seconds under load; 4s gives 1.3 seconds.

  The 7s retry budget follows from the same number. With `tries 2` and a 4s read timeout the implied ceiling is 8s, so a budget of 8s would never fire — a limit set exactly at the maximum the other settings already permit is decorative. Setting it to 7s leaves the second attempt 3 seconds, which is deliberately more than the 2700 ms I have observed. A tighter budget of 5s or 6s would leave the retry 1–2 seconds, structurally unable to complete the slowest endpoint I have measured, so the retry would be spent on an attempt that could not succeed.
- Alternative: Keep `proxy_read_timeout` at 3s and accept the 300 ms margin, or raise it further to 5s or more. A longer timeout holds worker connections open longer under load and delays the point at which a genuinely stuck backend is detected.
- Trade-off: A longer read timeout means a hung backend occupies a connection for longer before NGINX gives up, and the client waits longer for an eventual error. The worst case a client can now experience is 4s on the first attempt plus 3s on the retry, or 7 seconds before an error — a deliberate ceiling rather than an accident of the defaults, but a long time for a user to wait.
- Evidence / commit: 27db67f. The 2700 ms figure comes from eight application.log records in the 11:25–11:26 window, each reporting `status: 200` with `duration_ms: 2700` against access.log entries showing `status: 504` with `request_time: 2.001` for the same request_ids. Analysed in log_analysis.md Q8.
- Production improvement: 2700 ms is a single repeated value from a 30-minute synthetic dataset, not a latency distribution. It shows `/records` can take 2.7 seconds; it does not show it never takes 3.5. In production I would set timeouts from a p99 measured over a meaningful period, review them as the workload changes, and alert when p99 approaches the configured timeout — so the limit is adjusted before it starts generating 504s rather than after.
